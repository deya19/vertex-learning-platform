## Decisions and assumptions
- Use the current `@clerk/nextjs` SDK installed by `clerk init`; do not use `@clerk/clerk-react`.
- Keep `/` and browsing public. Do not add broad route protection or invent private routes that do not exist.
- Use Clerk's prebuilt `SignInButton`, `SignUpButton`, `Show`, and `UserButton` controls in the existing home header.
- Preserve the existing visual language and layout. Adapt the current avatar presentation only as needed to host `UserButton`; do not redesign the page.
- Keep `CLERK_SECRET_KEY` server-only. Do not read, print, commit, or hardcode values from `.env.local`; the CLI owns the generated environment configuration.
- The Clerk CLI may have installed global/project skills as part of init; do not add unrelated application behavior.

## Required implementation
1. Update `proxy.ts` so `config.matcher` contains `'/__clerk/:path*'` exactly once, after `'/(api|trpc)(.*)'`.
2. Update the home header in `app/page.tsx`:
   - When signed out, render clear sign-in and sign-up actions using Clerk components and links/buttons that fit the existing navigation.
   - When signed in, render `UserButton` in place of the hard-coded `A` avatar.
   - Preserve the notification bell as presentational-only.
   - Keep all existing public landing content and links intact.
3. Update `app/globals.css` only as necessary to make the auth controls fit the existing desktop and responsive header without changing the page design beyond the auth controls.
4. Leave the CLI-generated provider and sign-in/sign-up routes intact unless a verification failure requires a minimal correction. `ClerkProvider` must remain inside `<body>`.

## Security considerations
- Never expose or import `CLERK_SECRET_KEY` in client code.
- Do not use client-side auth state to protect server routes; no protected feature is being introduced in this small setup.
- Do not read or echo existing environment variable files.
- Keep authentication callbacks on the same-site Clerk-managed routes generated by the CLI.
